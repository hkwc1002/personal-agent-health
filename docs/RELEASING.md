# GitHub 发布流程

仅将本项目的公开源码目录作为仓库根目录。不要从外层运维目录执行 `git add .`，也不要上传生产健康服务目录。

## 发布前

1. 明确实际仓库所有者和名称 `OWNER/personal-agent-health`、许可证与公开范围。
2. 执行 `python3 -B scripts/test.py`，记录实际平台、通过及跳过结果。
3. 执行 `python3 -B scripts/check_release.py`。仅允许 `release-files.json` 列出的源码、文档和合成测试。未列出的文件、符号链接、常见密钥特征会导致失败；错误只给文件名和类别，不打印秘密值。
4. 在隔离 Linux 环境完成 Docker 构建、socket 测试及安装指南；在明确版本的 Hermes 上验证插件加载和实际工具调用。GitHub CI 尚未运行前不写“CI 已通过”。
5. 发布前检查 MIT 的授权范围和第三方数据说明。仓库不携带营养数据包、原健康库、生产日志、截图、账户信息或访问凭据。

## 准备干净源码包

```bash
python3 -B scripts/release.py --repository OWNER/personal-agent-health --output dist
```

这个命令只生成公开源码 ZIP 与 `SHA256SUMS`。它只打包允许清单中的文件，将 README 的仓库地址替换为实际 URL，并移除准备阶段提示。命令不会创建 GitHub 仓库，不运行 Git 提交，不上传文件。

把 ZIP 解压到新的空目录，以解压后的 `personal-agent-health/` 作为仓库根目录。此目录已经拥有实际安装链接，可重新运行发布检查和测试。不要连同 `dist/` 上传。

不要以旧运维仓库的 Git 历史创建公开仓库；历史中可能包含已经删除的秘密。按允许清单构建全新源码历史。

## 获得公开发布授权后

1. 创建正确所有者下的仓库，默认分支使用 `main`，按本项目根目录提交文件。
2. 检查暂存文件列表和 diff，确认没有 `data/`、`secrets/`、凭据、真实身份、生产回执或健康快照。
3. 推送并等待 CI。检查公开 README 中的一行安装入口可访问，所有相对链接有效。
4. CI 与实际安装验收通过后再创建 Alpha release，附上源码包、校验值、支持环境和未验证范围。
5. GitHub 安全功能允许时启用秘密扫描、推送保护和私密漏洞报告；未启用不能写成已启用。

如果凭据曾经进入任何公开提交，先撤销/轮换凭据，再清理历史。只删除当前文件不能消除历史泄漏。

## 发布阻塞条件

真实仓库地址未确定、源码扫描失败、测试失败、许可证来源不清或干净 Linux/Hermes 安装尚未验收时，不宣传“开箱即用的稳定版本”。允许在明确标注限制的私有候选仓库继续验收；公开上传仍需独立授权。
